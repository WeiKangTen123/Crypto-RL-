Signal API endpoint
What a provider integrates against. They pull market data / timestamps from us, and POST a signal when their model fires. We stamp as_of on receipt.

POST
https://btest.abcz-tr.com/api/v1/signals
⏱ as_of is stamped server-side on receipt — providers can't back-date a signal or claim latency they didn't have.
🔁 You own every decision. We execute the entries and exits you submit. You can also rest an explicit stop or take-profit at a price — set stop_loss_price / take_profit_price (absolute) and we fill at that level when a bar trades through it (worse, at the open, on a gap). We do not compute dynamic exits (trailing / percent-of-entry / ATR) — run those yourself and submit the exit as a signal (target: 0, or a flip). Dynamic / ambiguous stop fields are rejected, so your record is only ever your own calls.
Signal contract
Field	Type	Meaning
ts req	int (ns)	decision time (their bar)
symbol req	string	e.g. BTCUSDT
target req	float [-1,1]	desired position: +1 long … −1 short, 0 flat
strength	float	conviction — sizes the bet (higher = bigger, relative to your own calls)
margin	float ($)	optional sizing scheme → runs your scheme alongside ours
leverage	float	optional — with margin → notional = margin × leverage
notional	float ($)	optional — explicit Run B notional (instead of margin × leverage)
stop_loss_price	float ($)	optional — resting stop at an absolute price; filled AT the level when a bar trades through it
take_profit_price	float ($)	optional — resting take-profit at an absolute price (same fill model)
horizon	int (ns)	optional intended hold
reason	string	optional free text
as_of	int (ns)	server-stamped — ignored if sent

# provider POSTs its signal series (one submission → one scored run)

  -H "Authorization: Bearer sk_sig_…" \
  -H "Content-Type: application/json" \
  -d '{
    "strategy": "My Momentum Alpha",
    "symbol": "BTCUSDT", "resolution": "1d",
    "signals": [
      {"ts": 1700000000000000000, "target": 1.0},
      {"ts": 1701000000000000000, "target": 0.0}
    ]

Name the run with an optional top-level strategy — it labels this run in your Runs & History (falls back to your key's name if omitted), so one key can run many differently-named strategies. We replay the submitted series through the same deterministic engine (fills, fees, slippage, funding) — the score reflects OUR execution, not theirs. One submission → one run.
Sizing — want to set your own leverage?
Every run is graded on our standard sizing (Run A) — that's the grade of record, so results stay comparable across providers. If you also want your own leverage / margin measured, tag every signal with a sizing scheme and we'll additionally replay it as Run B and report the gap between the two.

Run A — standard sizing · always
# just direction + conviction — we size it
"signals": [
  {"ts": …, "target": 1.0, "strength": 0.8},
  {"ts": …, "target": -0.5, "strength": 0.3}
]
One fully-funded cross-margin book (≤1×, never levered): a lone position takes ≈95% of equity, N concurrent positions split it ≈95%/N. strength (optional) weights that split — higher-conviction calls get a bigger share.
Run B — your own leverage · optional
# add margin + leverage to EVERY signal
"signals": [
  {"ts": …, "target": 1.0, "margin": 500,  "leverage": 5},
  {"ts": …, "target": 1.0, "margin": 1000, "leverage": 3}
]
margin (USD) × leverage = your notional — or send an explicit notional. We replay your scheme alongside Run A; the A↔B gap = what your sizing is worth. Miss the scheme on any signal → Run B is skipped. (target still sets direction; your scheme sets size.)
The grade of record stays Run A either way — we never let a provider flatter the headline grade with their own sizing. Run B is shown as a side-by-side comparison in each run's report.
Levered / market-neutral books: also send a run-level leverage (e.g. 5) and Run B becomes a faithful levered lens — your real gross, with funding, slippage and maintenance-margin liquidation all modelled (a book the venue would have margin-called shows the real drawdown, even −100%). It's a display lens, never graded: leverage is a knob you can turn any day, not signal skill. So you get both — a comparable ≤1× grade (Run A) and your true levered curve (Run B), with a verdict on whether the leverage improved risk-adjusted return or just amplified variance toward ruin.
Multiple coins & custom backtest period
Two more knobs on a submission: run a multi-coin book, and pin the backtest window instead of letting it default to wherever your signals fall.

Multiple coins → one portfolio
# tag each signal with its own symbol
"signals": [
  {"ts": …, "symbol": "BTCUSDT", "target": 1.0},
  {"ts": …, "symbol": "ETHUSDT", "target": -0.5},
  {"ts": …, "symbol": "SOLUSDT", "target": 1.0}
]
All coins run in one fully-funded cross-margin book (≤1×, split across positions by conviction) → one equity curve, one grade for the basket. The top-level symbol becomes an optional fallback. Coins we have no price data for are skipped and listed as uncovered.
Custom period (optional)
# pin the window; omit → your signal span
{
  "resolution": "1d",
  "start": "2023-01-01",
  "end":   "2025-01-01",
  "signals": [ … ]
}
We replay over exactly [start, end] (clipped to available data). Time with no active signal is flat; signals outside are ignored. Handy to grade every provider on the same window. Omit both → first-signal … last-signal.
Honesty pays — declare your trials, claim your track
Two optional fields (Scorecard v2.1) let a serious provider prove their edge isn't luck — and unlock the top grade.

variants_tested — deflate your own Sharpe honestly
# how many variants did you try before this one?
{
  "variants_tested": 25,
  "signals": [ … ]
}
The best Sharpe of 25 attempts is much weaker evidence than a first-try Sharpe. The deflated-Sharpe test uses max(your declared count, your observed resubmissions of the same book) — so declaring honestly costs nothing extra, while resubmission farming raises your own bar automatically. Undeclared → we still count your family of submissions.
claimed — reconcile a real track, unlock grade A
# claim your return over the window (percent)
{
  "claimed": { "total_return_pct": 12.5, "tolerance_pct": 2.0 },
  "signals": [ … ]
}
We check our ≤1× replay against your claim: match within tolerance → the reconciled gate passes hard and grade A becomes reachable. Mismatch → DQ. No claim → grades cap at B (the score itself is never capped). Not combinable with run-level leverage > 1 — the claim is checked against the standard ≤1× book.

RULES
  - `target` is a POSITION I hold until my next signal changes it — not a per-trade order.
  - EXITS — TWO WAYS. (a) EXPLICIT price order: put `stop_loss_price` and/or `take_profit_price`
    (an ABSOLUTE price) on the signal that OPENS a position; the platform fills AT that level when
    a bar trades through it (worse, at the open, on a gap). (b) DISCRETIONARY / DYNAMIC exit
    (trailing, ATR, percent-of-entry): the platform does NOT compute these — I run the rule on MY
    side and emit the exit as a signal (`target: 0`, or a flip) at the bar it fires. The API REJECTS
    trailing_stop_pct / stop_loss_pct / stop_loss / etc. — only explicit *_price orders are executed.
  - `ts` must be a real PAST bar timestamp in nanoseconds.
  - Send the whole series in one POST; the JSON response is the scored run:
    run_id, total_return, sharpe, max_drawdown, final_equity_usd, grade, and a full
    `scorecard` — integrity gates (reproducible / no-lookahead / costs-real / reconciled)
    plus graded Edge / Robustness / Consistency / Cost on an adaptive lens. A hard gate
    failure disqualifies the run regardless of returns; short samples grade PROVISIONAL.
    If I sent a Run B scheme, the response also carries the Run A vs Run B sizing comparison.
